# Atlas SOC Lab — Troubleshooting & Incident Record

This document records every genuine technical problem encountered during the end-to-end build, configuration, and validation of the Atlas SOC Lab on **MacBook Air (Apple Silicon M5, 24 GB RAM, macOS 26.4 `arm64`)**, along with observed root causes, exact fixes applied, and verification outcomes.

---

| # | Phase / Component | Observed Symptom / Error | Root Cause | Exact Fix Applied | Verification Result |
|---|---|---|---|---|---|
| 1 | Part A — Apple Silicon VirtualBox Compatibility | Official VirtualBox 7.2 documentation explicitly states x86_64 VMs (Wazuh OVA & Windows Server 2025) cannot run on `arm64` hosts; no authorized x86_64 remote server existed. | Apple Silicon `arm64` lacks native x86_64 virtualization in VirtualBox. | Implemented **Option A (Hybrid UTM 5.0.9-2 / QEMU 10)**: native ARM64 Ubuntu 24.04.5 LTS (`WAZUH-ARM`, `-accel hvf`) + genuine x86-64 Windows Server 2025 Standard Evaluation (`ATLAS-SRV`, `-accel tcg,thread=multi`, `q35`, UEFI + `swtpm` TPM 2.0, VirtIO storage/NIC). | PASS — Both VMs run concurrently and stably within 12 GB combined RAM on 24 GB host. |
| 2 | Part B — Host-Only Subnet (`10.10.20.0/24`) | macOS `vmnet-host` initially assigned `192.168.128.1` instead of `10.10.20.1`. | In UTM/QEMU `vmnet-host`, `HostNetUuid` (`net-uuid`) and custom `start-address`/`end-address`/`subnet-mask` are mutually exclusive; setting `HostNetUuid` silently overrode the custom `10.10.20.0/24` subnet. | Removed `HostNetUuid` from both VMs' `config.plist` while keeping `Mode: Host`, `VlanGuestAddress: 10.10.20.0/24`, `VlanDhcpStartAddress: 10.10.20.1`, `VlanDhcpEndAddress: 10.10.20.200`, `IsolateFromHost: False`. | PASS — macOS created `bridge102` at `10.10.20.1/24`; Host↔VM and VM↔VM latency ~0.3–2 ms. |
| 3 | Part C — Ubuntu ARM64 `cloud-init` Provisioning | `WAZUH-ARM` ignored initial `wazuh-arm-cidata.iso` on first boot. | `hdiutil makehybrid` omitted RockRidge filenames (mangling `user-data`) and USB CD enumeration raced `cloud-init-local`. | Rebuilt `cidata` ISO with `mkisofs -volid cidata -joliet -rock` and attached as a read-only `VirtIO` disk. | PASS — `cloud-init` configured static `10.10.20.100/24`, SSH keys, and hostname on first boot. |
| 4 | Part C — Wazuh Installer Version | `https://packages.wazuh.com/4.14/wazuh-install.sh` installed **Wazuh `v4.14.11`** (`4.14.10` installer URL returned HTTP 403). | Upstream Wazuh 4.14 channel advanced to maintenance release `4.14.11`. | Installed official `wazuh-install.sh` (`v4.14.11`) on `WAZUH-ARM` and verified full compatibility with `wazuh-agent-4.14.10-1.msi` on `ATLAS-SRV`. | PASS — Manager `v4.14.11` and Agent `v4.14.10` connected and indexed alerts cleanly. |
| 5 | Automation — `utmctl` TCC Permission (`OSStatus -1743`) | `utmctl` CLI failed with `OSStatus error -1743` when invoked from non-interactive shell helper. | macOS Automation TCC denied AppleEvents from a helper process lacking `NSAppleEventsUsageDescription`. | Enabled localhost-only QEMU HMP monitors (`127.0.0.1:4444` for `ATLAS-SRV`, `127.0.0.1:4445` for `WAZUH-ARM`) and SSH key auth on both VMs (`qmon.py`). | PASS — Full autonomous snapshots (`savevm`), framebuffer screenshots (`screendump`), and reboots without disturbing user's desktop. |
| 6 | Evidence Collection — QEMU `screendump` Sandbox Denial | QEMU `screendump` returned `Operation not permitted` when targeting `VM.utm/Data/`. | UTM's `QEMULauncher` runs inside macOS App Sandbox and can only write to its App Group container. | Directed `screendump` output to `$HOME/Library/Group Containers/WDNLXAD4W8.com.utmapp.UTM/` and converted PPM→PNG via `sips` inside `qmon.py`. | PASS — Direct VM framebuffer captures work reliably in background without screen-recording full desktop. |
| 7 | Part D7 — DNS RPC Race Condition (`WIN32 1722`) | `Get-DnsServerResourceRecord` threw `WIN32 1722` (RPC Server Unavailable) immediately after `Restart-Service DNS`. | On emulated x86-64 TCG, the DNS Server RPC endpoint needed ~8–10 seconds to finish binding after service restart. | Added `Start-Sleep -Seconds 10` after `Restart-Service DNS` in `phase2_post_adds.ps1`, removed the NAT IP A-record, restricted DNS listeners to `10.10.20.10`, and disabled DNS registration on `Ethernet 2`. | PASS — `nslookup -type=A ATLAS-SRV.atlas.local 10.10.20.10` returns **only `10.10.20.10`**. |
| 8 | Part D8 — Evaluation Activation Forwarder | `ATLAS-SRV` could not resolve `www.microsoft.com` initially because it was authoritative for `atlas.local` with no forwarder. | Multihomed DC on macOS `vmnet-shared` uses `192.168.64.1` (not VirtualBox's `10.0.3.3`) as NAT DNS resolver. | Added `192.168.64.1` via `Add-DnsServerForwarder`, verified `Resolve-DnsName www.microsoft.com`, ran `slmgr /ato` and `slmgr /dlv`. | PASS — `Product activated successfully.` (`License Status: Licensed`, 180 days remaining). |
| 9 | Part F — Timestamp Correlation Clock Offset | Windows Event `4625` timestamp (`15:29:03.418Z`) was ~5.96 s ahead of Wazuh ingestion timestamp (`15:28:57.454Z`). | Emulated QEMU TCG guest software clock drifted slightly ahead of `WAZUH-ARM` NTP-synchronized UTC clock. | Documented the exact ~5.96 s offset in `SOC-Investigation-Ticket-ATLAS-001.md`, correlated unambiguously via `EventRecordID` (`2963`/`2962`/`2978`), and resynchronized time via `w32tm`. | PASS — Exact 1:1 event-to-alert correlation verified and documented. |
| 10 | Part E / Appendix E — `wazuh-logtest` Rule `5716` vs `5760` | Testing `Failed password for svc_backup` matched Rule `5760` instead of `5716`. | In Wazuh 4.14.11 stock `0095-sshd_rules.xml`, `Failed password` matches child Rule `5760` (`T1110.001`), while `Failed none` matches parent Rule `5716` (`T1110`). | Verified both patterns in `wazuh-logtest` (`tests/wazuh-logtest-t5-5716.txt`) and validated Windows Custom Rule `100100` live against real Windows Event ID `4625` (`RecordId 2978`). | PASS — Both `5716`/`5760` decoder validation and live level-10 Rule `100100` alert verified. |
| 11 | Part G2 — `suricata.exe` Exit Code `-1073741515` (`0xC0000135`) & Npcap NSIS Wizard | `suricata.exe -V` and `-T` exited silently with `-1073741515` (`STATUS_DLL_NOT_FOUND`); initial Win32 `BM_CLICK` on Npcap 1.90 "Install" button did not advance NSIS wizard. | Suricata 8.0.8 links dynamically against Npcap's `wpcap.dll`; Npcap 1.90 requires interactive Session 1 installation, and NSIS `Install` button requires `WM_COMMAND` + `GetDlgCtrlID` with exact label matching (avoiding checkbox prefix collision). | Unlocked `ATLAS-SRV` Session 1 and installed Npcap 1.90 via exact-match `WM_COMMAND` automation (`install_npcap_uia.ps1`). Verified `wpcap.dll = True`, `Suricata version 8.0.8 RELEASE`, and `suricata -T` succeeded (`Configuration provided was successfully loaded. Exiting.`, recording the expected non-fatal `threshold.config` warning). | PASS — Npcap 1.90 + Suricata 8.0.8 validated cleanly (`tests/atlas-srv-npcap-suricata-verify.txt`). |
| 12 | Evidence Capture — QEMU HMP `sendkey` on Locked Windows Console | QEMU HMP `sendkey ctrl-alt-delete` and `sendkey` password strokes did not reach Windows Server 2025 Lock Screen while SPICE held the console. | Windows Server 2025 console session was logged out after AD DS promotion reboot, and SPICE/USB HID intercepted HMP keyboard injection. | Verified SAS trigger via `sas.dll` (`SendSAS(false)`) and used a one-time `Winlogon` `AutoAdminLogon` (`AutoLogonCount = 1`) paired with an immediate logon cleanup task that erased `DefaultPassword` and reset `AutoAdminLogon = 0` upon Session 1 activation. | PASS — `ATLAS\Administrator` Console Session 1 activated cleanly; verified `DefaultPassword` deleted and `AutoAdminLogon = 0`. |
| 13 | Operations — Isolated `WAZUH-ARM` Clock Drift After Host Sleep | After pausing the Mac host overnight while `WAZUH-ARM` had `eth-nat DOWN` (no NTP access), `WAZUH-ARM`'s guest UTC clock lagged host UTC by ~6 hours. | Without internet NTP access on an isolated Host-Only VM, guest monotonic time pauses during macOS host sleep. | Resynchronized `WAZUH-ARM` UTC time directly from the macOS host (`sudo date -u -s "<UTC>"`) before live Part G alerting and dashboard screenshot verification. | PASS — `WAZUH-ARM` UTC clock synchronized to exact host UTC before live Suricata alert ingestion. |
| 14 | Part G2 — Suricata `flags:S;` vs macOS RFC 3168 ECN/CWR SYN Packets | Suricata captured `10.10.20.1 -> 10.10.20.10:8088` flows & HTTP 401 transactions in `eve.json`, yet `sid:1000001` (`flags:S;`) logged `alert: 0`. | Live `eve.json` flow telemetry revealed `"tcp_flags_ts":"d3", "syn":true, "ecn":true, "cwr":true`: macOS sets RFC 3168 ECN (`ECE`+`CWR`, `0xC2`) on outgoing TCP SYN packets by default, whereas bare `flags:S;` matches only when `ECE=0` and `CWR=0`. | Updated `atlas-test.rules` (`sid:1000001; rev:3;`) to use official Suricata mask syntax `flags:S,12;` (ignoring ECN bits `1` & `2` while strictly requiring SYN-only). | PASS — Verified live `"ATLAS LAB portal TCP test"` alert in both `eve.json` and Wazuh Threat Hunting (`rule.id: 86601`). |
| 15 | Post-Reboot Validation — `WAZUH-ARM` UEFI Warm Reset Quirk under Apple HVF | After in-guest `sudo reboot` on `WAZUH-ARM`, QEMU remained running with `Display output is not active.` and no response on `10.10.20.100`. | Known QEMU 10 / UTM ARM64 UEFI (`-accel hvf`) quirk where in-guest `PSCI SYSTEM_RESET` stalls before firmware re-entry. | Issued clean hardware reset via QEMU HMP `system_reset` (`qmon.py wazuh-arm cmd "system_reset"` — equivalent to Restart/Stop→Start in UTM toolbar). | PASS — `WAZUH-ARM` booted cleanly in ~20 s with `eth-atlas 10.10.20.100/24`, `eth-nat DOWN`, and all 4 Wazuh services `active`. |
